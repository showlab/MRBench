“Plurality is never to be posited without necessity.”William of Ockham

Abstract

Recent advances in multi-robot manipulation have shown how robots can collaborate to accomplish complex tasks. However, successful coordination does not reveal which robots are actually needed. The same task may require different teams as robot capabilities change, resources become unavailable, or objects replace robotic support. We argue that reliable multi-robot manipulation requires physical necessity reasoning: understanding what a task demands, which resources can fulfill those demands, and which are truly necessary. We introduce MRBench, a benchmark for physical necessity reasoning in heterogeneous multi-robot manipulation. It comprises eight tasks with distinct concurrency and reach constraints, each evaluated under five configurations that change the required resources while preserving the task goal. Our evaluation reveals that existing coordination agents perform well with reference teams but struggle when robot embodiments change or passive objects can replace robotic support. To address this gap, we propose MRScissors, which separates task requirements from measured physical capabilities and identifies minimal feasible teams through constrained search. Across two model backbones, MRScissors achieves 85.4% and 91.2% team-selection accuracy, outperforming the strongest baselines by 10.4 and 9.5 points, respectively. Together, these findings expose a critical gap between coordinating robots and understanding their physical necessity.

BenchmarkOverview

Two suites, five configurations

A task is a set of jobs done by doers. It needs several arms when jobs at different places must happen at once (Concurrency) or lie beyond one arm's reach (Reach). Five configurations keep each task's goal and change only its doers, so the smallest team that can do it changes while the instruction does not.

How every scene is built

One table has three fixed places, west, south and east, and a fourth, north, for the surplus arm; each takes a Franka, a PiPER or an SO-101 (Isaac Sim 4.5, Isaac Lab 2.1). The right team is computed, from IK with margins and an exact search for the smallest feasible teams, then checked in simulation.

The protocol: four conveniences removed

It removes four conveniences that multi-robot benchmarks offer and real workcells do not.

01

No team is given

A method gets the goal, each arm's model, place and orientation, and the objects, but no role, skill list or reach.

02

Feasibility is not promised

14 of the 40 versions are infeasible, and “these jobs cannot all have a doer” is then the answer.

03

Names do not decide

A prop and its distractor look alike, and masses are given only within a factor of 0.75 to 1.3, so fitness must be measured.

04

Failure is not proof

A failed run's report names the jobs whose signals fired; only such a signal, not a missed grasp, counts against a smaller team.

MethodModel and code

MRScissors

The model writes what the task needs as a job graph, code measures who can do it into a capability table, and an exact search over that table returns the fewest arms.

  1. Job graph from a blind prover

    One session writes the jobs, their sites and groups from the goal and the scene. It is not told which arms exist, so it cannot write the task to suit them.

  2. Measured capability table

    Code fills every cell from tool results: who_can for every arm at every site, meet for hand-overs, measure for objects.

  3. Exact search and certificate

    From one arm up, it returns every smallest team, with what each arm's removal leaves undone and each object used or rejected.

  4. Stand-in objects

    When no team exists, the prover, still blind, is told which jobs lack a doer and asked what on the table could take them over.

  5. Review with unequal burdens

    Two reviewers, blind to each other, look for what was written easier or harder than the task; every edit cites its own tool call.

ExperimentsOne shot

Main results

Five methods, each given the same information, tools and output form, answer all 480 scenes in one shot with Qwen3.8-Max and with Claude Sonnet 5.5. Feasible answers are then carried out in Isaac Sim by a shared executor.
